# ADR-0005：物理文件夹与逻辑集合的组织模型

- 状态：已接受
- 日期：2026-07-30

## 背景

资源库本质上是一个普通文件夹，用户又希望尽量在 MO Gallery Desktop 内操作。应用需要决定如何呈现和修改库内目录树，以及是否同时提供不改变磁盘路径的逻辑集合。

## 共同定义

- **文件夹**对应资源库中的真实磁盘目录；在应用内移动资产到另一个文件夹，会移动原文件并原子更新资产路径。
- **集合**是数据库中的逻辑分组，不移动原文件；同一资产可以加入多个集合。
- **标签**是跨文件夹、跨集合的检索维度，也不改变原文件路径。

## 候选方案

### A. 文件夹 + 集合 + 标签（建议）

左侧同时呈现真实文件夹树和逻辑集合；资产可以通过应用内命令移动文件夹，也可以加入多个集合和标签。

优点：既保持磁盘结构透明，又支持不复制文件的灵活整理，接近 Billfish/Pixcall 类资源管理体验。

代价：MVP 模型和界面比只做目录浏览更复杂；必须用不同图标和文案避免用户混淆“移动到文件夹”和“添加到集合”。

### B. 只使用真实文件夹 + 标签

不实现逻辑集合。用户通过目录树和标签组织照片。

优点：磁盘事实和应用视图高度一致，模型简单，迁移后仍可从目录结构理解照片。

代价：一张照片只能位于一个文件夹，无法在不复制文件的情况下同时归入多个主题分组。

### C. 文件夹只作为底层位置，主要使用集合 + 标签

界面弱化真实目录树，用户主要通过逻辑集合整理。

优点：整理自由度高，用户较少直接触发磁盘移动。

代价：资源库是普通文件夹的透明性下降；在资源管理器中看到的结构和应用组织方式不一致。

## 决策

采用 **方案 A：文件夹 + 集合 + 标签**。

- 文件夹树映射资源库内的真实磁盘目录；
- 应用内“移动到文件夹”会移动原文件并更新资产相对路径；
- 集合是库内数据库中的逻辑分组，同一资产可加入多个集合；
- 标签是跨文件夹、跨集合的检索维度；
- 集合和标签均不得改变原文件路径。

## 交互约束

- 使用不同图标和文案区分文件夹与集合；
- 会修改磁盘路径的命令必须写作“移动到文件夹”；
- 只修改逻辑关系的命令必须写作“添加到集合”；
- 拖放目标是文件夹时执行文件移动，目标是集合时只创建集合关系；
- 文件移动失败时不得提前更新索引；集合关系不依赖文件移动。

## 后果

- 需要 `Folder` 的磁盘投影视图以及 `Collection`、`CollectionAsset` 等持久化模型；
- 文件夹不应作为独立事实重复存储，扫描磁盘即可重建目录树；仅保存 UI 展开状态等非事实数据；
- 集合与标签属于不可由原文件重建的用户数据，必须随资源库迁移和备份。
