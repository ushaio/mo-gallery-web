# ADR-0017：单资源库规模与性能目标

- 状态：已接受
- 日期：2026-07-30

## 背景

资源库包含静态成片、HEIC/TIFF 和大型 RAW。目标规模决定数据库索引、扫描算法、缩略图队列、文件监听方式和前端虚拟化要求。没有数量级目标就无法定义“快速浏览”和“启动扫描完成”的验收标准。

## 候选规模

### A. 面向个人摄影库：10 万资产（建议）

- 设计上支持单库 100,000 项资产；
- 常用列表和筛选必须分页/游标查询，前端网格虚拟化；
- 打开已有库时先显示数据库中的结果，校准扫描在后台进行；
- 新增/变化项增量刷新，不等待全库扫描完成；
- 缩略图按可视区域优先，后台队列限流。

这是个人摄影师与长期照片归档较现实的上限，同时仍适合单机 SQLite 和单当前库模型。

### B. 轻量资源库：2 万资产

实现和测试成本较低，但几年照片积累或 RAW+成片并存很容易超过该规模。

### C. 专业大型 DAM：50 万资产以上

需要更严格的分片扫描、目录级变更标记、缓存治理、数据库维护和压力测试，可能超出当前 Desktop 首期投入。

## 建议的首期性能验收（基于 A）

- 已建立索引的 10 万资产库，打开后 2 秒内显示首屏缓存结果；
- 普通排序/筛选查询在本地数据库中 P95 小于 300 ms；
- 网格滚动不一次性把全部资产加载到 React；
- 启动校准在后台运行，不阻塞浏览已索引资产；
- 新增一个普通 JPEG 后，运行时监听在 3 秒内将其显示为待处理或已索引；
- 缩略图生成并发可配置/限流，不让大批 RAW 使界面失去响应；
- 10 万资产首次初始化允许长时间后台处理，但必须持续展示已发现、已索引、失败与剩余状态，并支持退出后续跑。

具体时间需要在目标硬件和样本库上基准测试后校准，不能仅靠单元测试声称达标。

## 决策

采用 **方案 A：按单资源库 100,000 项资产设计**。

### 架构约束

- SQLite 查询使用分页或游标，不向前端返回全库数据；
- React 资产网格必须虚拟化，只渲染可视范围及少量缓冲项；
- 打开已有资源库时先显示数据库现有结果，一致性扫描在后台执行；
- 文件发现、元数据提取和预览生成使用分阶段有界队列；
- 可视范围和用户当前选中项具有更高缩略图优先级；
- 首次初始化和未完成任务支持下次打开继续，不把“退出应用”视为失败；
- 不在首期扫描路径中同步计算完整内容哈希。

### 首期目标

- 已索引 100,000 项的基准库，打开后目标 2 秒内显示首屏缓存结果；
- 常用排序/筛选本地查询目标 P95 小于 300 ms；
- 运行时新增普通 JPEG 后，目标 3 秒内显示为待处理或已索引；
- 网格滚动不得一次加载或渲染全部资产；
- 后台扫描和 RAW 预览任务不得让导航、筛选和选择操作失去响应；
- 首次扫描持续展示发现、索引、预览失败和剩余任务状态。

这些时间是设计目标，不是脱离硬件的绝对承诺。实施时需定义基准硬件和 100,000 项混合格式样本库并记录实测结果。

## 后果

- 不能以简单的递归扫描完成后一次性写库/渲染实现；
- SQLite 需要针对路径、状态、拍摄时间、评分、颜色、收藏和关联表建立实测索引；
- 文件监听事件需批处理和去抖，避免大量复制时产生 UI 更新风暴；
- 首期测试除功能测试外必须包含规模基准测试。
