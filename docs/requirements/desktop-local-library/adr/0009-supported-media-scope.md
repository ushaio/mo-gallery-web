# ADR-0009：首期媒体类型与格式范围

- 状态：已接受（失败行为仍由 ADR-0010 决定）
- 日期：2026-07-30

## 背景

需求目标是管理本地照片资源。不同图像格式需要不同的解码、缩略图、色彩管理和元数据能力。仅扫描扩展名而不能稳定生成预览的文件，不应被宣传为完整支持。

## 支持等级定义

- **完整支持**：可索引、生成缩略图、查看大图、读取基础尺寸，并尽可能提取 EXIF；
- **占位支持**：可登记文件和显示通用图标，但不能稳定预览；
- **不支持**：扫描器忽略，不建立资产记录。

## 候选方案

### A. 首期只完整支持常见静态成片格式（建议）

完整支持 JPEG/JPG、PNG、WebP；是否纳入 AVIF 取决于 Go 解码链路验证。GIF 可按静态首帧处理或首期忽略。HEIC/HEIF、TIFF、相机 RAW 和视频不纳入首期。

优点：能够保证扫描、缩略图和预览闭环，依赖和打包风险最低。

代价：手机 HEIC 和摄影 RAW 用户首期无法管理全部照片。

### B. 首期覆盖常见照片格式，包括 HEIC 与 TIFF

完整支持 JPEG、PNG、WebP、HEIC/HEIF、TIFF，并明确 GIF 的静态/动态行为；RAW 后续支持。

优点：更符合现代手机照片库和扫描照片场景。

代价：需要引入并验证 HEIF/TIFF 解码、Windows 打包、EXIF 方向和色彩配置，首期范围扩大；macOS 打包留到后续平台交付阶段验证。

### C. 首期包含相机 RAW

在 B 基础上支持主流 RAW（如 CR2/CR3、NEF、ARW、DNG、RAF、RW2），优先提取内嵌预览，不做 RAW 显影。

优点：适合摄影资产管理的核心用户。

代价：格式矩阵、元数据和预览兼容性复杂；“可索引但无预览”的失败状态必须产品化；不同厂商格式需要真实样本验证。

## 明确非目标

- 首期不提供照片编辑或 RAW 显影；
- 不修改原文件的 EXIF/IPTC/XMP；
- 标签、集合、评分等组织数据只写入 `library.db`；
- 视频、音频、字体和设计源文件需要单独决策，不能因“资源”一词默认纳入。

## 决策

采用 **方案 C：首期包含相机 RAW 的资产管理与预览支持**。

首期格式范围：

| 类别 | 格式 | 支持目标 |
|---|---|---|
| 常见静态图像 | JPEG/JPG、PNG、WebP | 索引、缩略图、大图预览、尺寸和可用元数据 |
| 手机/高位深图像 | HEIC/HEIF、TIFF | 索引、缩略图、大图预览、尺寸和可用元数据 |
| 相机 RAW | CR2/CR3、NEF、ARW、DNG、RAF、RW2 | 索引、EXIF 和内嵌预览提取，不做 RAW 显影 |

GIF、AVIF 及其他 RAW 厂商格式不因本决策自动纳入。GIF 与 AVIF 的后续决定见 ADR-0035：GIF 网格使用静态首帧、预览播放原动画，AVIF 首期正式支持静态单帧。

### RAW 支持边界

- 优先提取 RAW 文件中的内嵌 JPEG 预览或缩略图；
- 不执行 RAW 马赛克解码、白平衡、色彩转换、镜头校正或其他显影；
- 不修改 RAW 原文件，不写入 EXIF/IPTC/XMP；
- 标签、集合、评分和自定义标题只写入 `library.db`；
- “支持某扩展名”必须以真实厂商样本通过索引、预览和 EXIF 验收为准。

### 现有实现差距

当前 Desktop 只有 `goexif`，没有 HEIC、TIFF 或 RAW 预览解码链路。实现前必须选定并验证媒体探测、内嵌预览提取和缩略图后端，并在当前交付范围内完成 Windows 10/11 x64 打包验证；不能只增加扩展名扫描。macOS 打包行为在后续平台交付阶段单独验证。

## 后果

- 首期测试矩阵需要覆盖每种格式的多个真实设备样本、旋转方向、损坏文件和无内嵌预览 RAW；
- 需要区分“文件格式已识别”“元数据可读”“预览可生成”三个能力状态；
- RAW 原文件通常较大，扫描不得默认同步计算全文件 SHA-256，否则大库首次扫描成本不可控；
- 无法提取内嵌预览时是否仍建立资产，由 ADR-0010 决定。
