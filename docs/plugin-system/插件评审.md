## 评审范围调整

本记录评审对象从“存储插件功能”提升为 Desktop 系统插件管理层。系统插件管理层
（Plugin Core）只评审插件的目录与安装包、信任校验、版本与回滚、进程生命周期、
能力注册与路由、权限、凭据、审计、设置入口和分发边界。

`storage@1` 是当前唯一落地的能力域，也是系统插件管理层的迁移基线。对象 key、
照片、缩略图、S3、上传预处理和 URL 生命周期等业务语义仍由 storage capability
负责，不上提为 Plugin Core 的通用接口。

本记录不把 `desktop/agent_extensions/` 直接并入系统插件，也不因系统级定位默认
开放任意 UI、Wails、数据库、文件系统或 shell 能力。插件市场只读取宿主内置的可信索引源，不接受 renderer 传入任意仓库地址；设置入口
提供“插件市场 / 已安装”两个视图。

## 结论

当前实现已经包含插件目录、独立进程、JSON-RPC、双向文件传输、Node
运行时、签名包、版本回滚、凭据存储、Schema 配置 UI 和离线登记补偿，实际
复杂度已经覆盖系统插件管理层的大部分基础设施，而当前只有一个
`storage@1` S3-compatible 能力域。

因此，插件功能的产品定位调整为 Desktop 系统插件管理层：核心平台负责安装、
信任、生命周期、权限、凭据、审计和能力路由；具体业务功能由独立、可版本化的
能力域按真实需求逐步接入。当前尚未达到生产交付条件，优先补齐管理层的完整性
校验、依赖感知卸载、能力权限隔离和发布边界，再继续抽取通用核心或新增能力域。

## 管理层验收边界

系统插件管理层在进入生产前至少需要满足：

1. 发现、安装、启用、停用、更新、回滚和卸载均经过统一目录与状态机管理。
2. 生产模式在发现和启动时重新校验签名、checksum、核心协议版本和 contribution
   兼容性；开发模式的未签名状态必须显式可见。
3. 插件崩溃、超时、取消和资源回收不会拖垮 Desktop 主进程；能力调用只能经由
   对应 broker，不能直接访问 Wails bindings、数据库或任意本地路径。
4. 权限按 capability 和资源范围授权，凭据按插件 ID、能力域和实例隔离，并留下
   脱敏审计记录；contribution 或权限指纹变化时，旧授权需要重新确认。
5. 设置页提供“插件市场 / 已安装”，展示版本、发布者/签名状态、运行时状态和 contributions；
   卸载插件时停止其 source 运行时，但保留 source 配置和凭据；重新安装同一插件后恢复使用。
6. 市场索引和包下载只允许内置 HTTPS 信任边界；发布包只携带当前目标平台所需 runtime。

以上是系统插件管理层的准入条件，不代表每个能力域都必须同时实现所有未来能力。

## 已确认问题

| ID | 层面 | 优先级 | 问题 | 影响 | 处理方向 |
|---|---|---|---|---|---|
| PLUG-SEC-01 | 系统管理层 | P1 | 已安装插件在发现和启动时未强制要求签名与 checksum 仍然有效 | 手工放入目录或安装后被修改的代码仍可能启动并读取凭据 | 生产模式每次启动前重新校验；只有开发模式允许未签名目录 |
| PLUG-STO-01 | storage@1 | P1 | Desktop UI 删除照片时请求删除缩略图，但 Web 明确拒绝 Desktop 插件对象删除 | 插件照片无法通过现有流程正常删除 | Desktop 先通过 storage capability 删除对象，再只删除云端元数据；明确支持“仅解除关联” |
| PLUG-MEDIA-01 | storage@1 | P1 | 插件上传分支没有执行 `StripGPS`，WebP 压缩选项也被静默忽略 | 隐私设置失效，上传结果与 UI 选择不一致 | 上传前在 Host 完成统一媒体预处理；不支持的组合必须显式报错 |
| PLUG-URL-01 | storage@1 | P1 | 临时/签名 URL 被当成长期 URL 写入 Photo，Web 无法调用 Desktop 插件刷新 | URL 到期后公开图库和缩略图失效 | Web 可见照片只接受稳定公开地址或服务端可刷新的代理地址；临时 URL 不作为永久地址 |
| PLUG-REL-01 | 系统管理层 | P2 | 每个平台构建嵌入并首次运行解包全部五个平台 Node runtime | 安装包和本地占用显著增加，发布链路复杂 | 每个目标只打包当前平台 runtime，或把 runtime 作为签名的按需组件 |
| PLUG-MKT-01 | 系统管理层 | P2 | 官方插件需要统一发现与安装入口 | 独立 release 不利于生产用户发现和更新 | 已实现内置索引、缓存、平台选择、安全下载与现有安装校验链路 |

其中 `PLUG-SEC-01`、`PLUG-REL-01` 和 `PLUG-MKT-01` 属于系统插件管理层；其余
三项属于 `storage@1` 能力域迁移问题。能力域问题必须闭环，但不能据此把 Plugin
Core 设计成存储业务 API 的集合。

## 代码证据

- `desktop/storage_plugins/catalog.go`：签名状态目前主要作为描述信息返回。
- `desktop/storage_plugins/manager.go`：source 创建和进程启动没有以 verified
  状态作为生产模式前置条件。
- `desktop/frontend/src/pages/PhotosPage.tsx` 与 `hono/photos.ts`：删除参数和
  Desktop 插件对象只读规则冲突。
- `desktop/services/upload.go`：GPS/WebP 参数只进入 Web multipart 分支，插件
  分支直接上传本地处理结果。
- `../mo-gallery-plugin-s3/src/plugin.ts`：signed 模式返回会过期的临时 URL。
- `desktop/storage_plugins/runtime_embed.go` 与 `.github/workflows/release.yml`：
  runtime 资产以整目录嵌入每个目标构建。

## 执行结果（2026-08-16）

- 新增 `desktop/plugin_core/`，提供核心协议版本、contribution 解析、能力域隔离和授权 broker。
- `storage_plugins` 保留为 `storage@1` 兼容适配层；旧 manifest 仍可安装，系统 manifest 支持
  `coreApiVersion`、runtime 对象、`contributions` 和 `permissions`。
- 生产模式创建 source 和启动 runtime 前均强制重新校验 checksum、签名和 manifest；未验证插件
  不会读取凭据。UI contribution 会被标记为 incompatible 并拒绝启动。
- Desktop 插件照片删除改为先经 storage broker 删除对象，再删除 Web 元数据；仅解除关联不会删除对象。
- 插件上传在 Host 统一执行 GPS 清理；WebP 插件压缩不支持时上传前明确报错；临时/签名 URL 不再登记为
  Web 照片永久地址。
- 设置入口提供“插件市场 / 已安装”，市场使用内置索引并在下载后继续执行完整包签名和兼容性校验。

本次通过：`cd desktop && go test ./...`、`cd desktop/frontend && npm run build`、根目录
`pnpm run build`、SDK/S3 `tsc --noEmit`，以及编译后 SDK contract tests（3/3）。SDK/S3
基于 `tsx` 的原始测试命令在当前 Windows 环境仍会触发 `spawn EPERM`。
